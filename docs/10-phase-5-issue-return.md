# 10 — Phase 5 Issue Records and Returns

## Delivered scope

Phase 5 turns the Phase 4 Receiver and Inventory directories into an operational
Issue-and-Return workflow. Admins and Workers can now:

- create one multi-material Issue Record for an active Receiver;
- issue reusable quantity stock, consumables and serialized asset units;
- find outstanding records across shifts;
- record full or partial Returns;
- capture the condition and disposition of each returned serialized unit;
- review Issue details, outstanding balances and an append-only Return timeline;
- search paginated Issue and Return activity appropriate to their role; and
- safely retry Issue and Return submissions without creating duplicate records or
  applying inventory changes twice.

AssetDesk remains a free university custody-tracking system. This phase contains
no price, payment, billing, fine or other financial transaction data.

## Architecture and records

The shared `@assetdesk/contracts` package defines strict Zod request and response
schemas for both the API and React application. MongoDB stores an Issue as the
long-lived custody record, with immutable snapshots of the Receiver, issuing
Admin or Worker, and each material as they appeared when the Issue was created.
Later edits to a directory entry therefore do not rewrite historical evidence.

Every Issue receives a sequential public ID in this form:

```text
GEU-ISS-YYYY-NNNNNN
```

The year and date calculations use Indian Standard Time. `issuedAt` and
`returnedAt` are generated by the server; they are not accepted from the browser.
Each material line has an immutable UUID line ID, issued quantity and mutable
outstanding quantity. Serialized lines also snapshot every asset tag, serial
number and condition at issue.

Return events are embedded as immutable history within the Issue Record. Each
event records its own UUID, server time, performing actor, returned items,
remaining outstanding count, resulting Issue status and whether it completed the
Issue. The current outstanding balance is also stored on the Issue for efficient
search and validation. An Issue can hold at most 100 Return events. Before each
partial Return, the server reserves enough remaining event capacity to guarantee
that all outstanding quantity lines and serialized assets can still be completed
within MongoDB's document-size limit; near the limit, the operator must submit a
larger batch.

## Creating an Issue Record

The responsive creation flow is deliberately guided for staff who do not use
specialist inventory software:

1. Search for and select one active Receiver.
2. Search active Inventory and add one or more material lines.
3. Enter a quantity for quantity-tracked material, bounded by current available
   stock, or select specific available asset units for serialized material.
4. Choose the expected Return preset when any selected line is reusable.
5. Optionally enter a purpose and operational notes.
6. Review Receiver, material, quantity, asset and due-date details before the
   final submission.

One material can appear only once in a request, and asset tags must be unique
within and across lines. A request supports up to 50 material lines and up to 100
serialized assets. The server re-reads and validates all selected records inside
the transaction; browser availability is never treated as authoritative.

Reusable material requires one of these due choices:

```text
ONE_DAY
ONE_WEEK
ONE_MONTH
SIX_MONTHS
ONE_YEAR
CUSTOM
```

Day, week, month and year presets use IST calendar arithmetic. Month and year
calculations cap to the last valid day when the original day does not exist in
the target month. A custom date must include an offset and be later than the
server-generated issue time. A consumable-only Issue cannot have a due date.

Issue creation uses one MongoDB transaction to validate the active actor, claim
the active Receiver, recheck material and asset availability, update inventory,
allocate the Issue ID, save the Issue and append its audit event. A concurrent
Receiver deactivation or stock change therefore causes the operation to fail
instead of leaving a partial record.

## Inventory effects

Inventory mutations depend on tracking mode and Return policy:

| Operation                                  | Material or asset transition                                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| Issue reusable quantity                    | `availableQuantity` decreases and `issuedQuantity` increases                                                 |
| Return reusable quantity                   | `issuedQuantity` decreases and `availableQuantity` increases                                                 |
| Issue consumable quantity                  | `availableQuantity` and `totalQuantity` decrease; nothing becomes outstanding                                |
| Issue serialized unit                      | Unit `AVAILABLE → ISSUED`; material available decreases and issued increases                                 |
| Return serialized as available             | Unit `ISSUED → AVAILABLE`; material issued decreases and available increases                                 |
| Return serialized with another disposition | Unit `ISSUED → UNDER_REPAIR`, `DAMAGED` or `LOST`; material issued decreases but available does not increase |

Consumables are permanently consumed at Issue time and cannot be returned. A
consumable-only Issue stays as an `ISSUED` historical record with a zero
outstanding balance and is excluded from Return search.

## Recording a Return

The `/returns` workspace supports cross-shift handling even when another person
created the Issue. A Worker must enter a complete Issue ID or asset tag, which
prevents the endpoint from becoming a browse-all directory. An Admin can also use
paginated fuzzy search across outstanding Issue, Receiver, material, asset-tag
and serial-number snapshots. The selected record opens a mobile-friendly Return
form containing only outstanding reusable items.

A Return may contain any subset of the outstanding items:

- quantity lines accept a positive quantity no greater than the outstanding
  balance; and
- serialized lines accept individual asset tags, each with a required condition
  and a disposition of `AVAILABLE`, `UNDER_REPAIR`, `DAMAGED` or `LOST`.

The API rejects duplicate lines or asset tags, tracking-mode mismatches,
consumables, over-returns, assets not belonging to the Issue, and assets already
processed by an earlier Return. The material, asset-unit, Issue balance, embedded
Return event and audit event are saved in one MongoDB transaction.

Issue status is derived after every Return:

```text
outstanding items remain  -> PARTIALLY_RETURNED
all resolved, any LOST    -> LOST
all resolved, any DAMAGED or UNDER_REPAIR -> DAMAGED
all resolved, no adverse outcome -> RETURNED
```

`LOST` takes precedence over `DAMAGED` when both outcomes exist across partial
Returns. `CANCELLED` remains in the shared domain vocabulary but Phase 5 does not
provide a cancellation operation.

## Idempotency and transactional safety

Both write endpoints require an `Idempotency-Key` header containing 16–128 safe
ASCII characters. AssetDesk stores only a SHA-256 hash of that key together with
a deterministic request fingerprint; the raw key is not written to the database,
audit metadata or API response.

The first successful write returns HTTP `201` with
`meta.idempotentReplay: false`. Retrying the same operation with the same key and
payload returns the already-saved result with HTTP `200` and
`meta.idempotentReplay: true`, without repeating inventory or audit mutations.
Using the same key for a different request returns a conflict. Unique database
indexes also protect concurrent retries that arrive before the first response.
Production startup explicitly creates/verifies every declared database index and
fails if the required uniqueness guarantees cannot be established.

MongoDB transactions require a replica-set deployment such as MongoDB Atlas.

## Authorization and visibility

All Phase 5 routes require an authenticated Admin or Worker with full account
access. Mutation routes additionally require a trusted Origin and a valid CSRF
token, and all Issue and Return responses are marked `no-store`.

- Admins can list and inspect all Issue Records and Return events.
- Workers list Issues they created or on which they personally recorded a
  Return, and list only Return events they performed.
- An Admin, the Issue creator, or a Worker who performed a Return receives full
  Issue history.
- Any other authenticated Worker can receive a restricted `RETURN_ONLY` view
  while the Issue is outstanding, so a different shift can complete the Return.
- An unrelated Worker cannot retrieve a completed Issue or another Worker's
  standalone Return event.

Worker cross-shift lookup accepts only an exact canonical Issue ID or asset tag.
Admin and role-scoped activity searches escape user text before constructing
regular expressions, correlate material/asset matches with outstanding lines,
and use pagination limits.

## API endpoints

```text
GET  /api/v1/issues
POST /api/v1/issues
GET  /api/v1/issues/return-search
GET  /api/v1/issues/:issueId

POST /api/v1/issues/:issueId/returns
GET  /api/v1/returns
GET  /api/v1/returns/:returnEventId
```

`GET /api/v1/issues` accepts `page`, `pageSize`, `search` and `status`.
`GET /api/v1/issues/return-search` accepts `page` and `pageSize`; Workers must
provide a complete Issue ID or asset tag, while Admins may provide a search term
of at least two characters. `GET /api/v1/returns` accepts `page`, `pageSize` and
`search`.

Admin search covers public identifiers and operational snapshots such as
Receiver, material, asset tag and serial number. The exact fields returned still
follow the role and `FULL`/`RETURN_ONLY` rules above.

## Web experience

Phase 5 adds these lazy-loaded authenticated routes:

```text
/issues                         searchable Issue list
/issues/new                     guided multi-item Issue flow
/issues/:issueId                Issue detail and Return timeline
/issues/:issueId/return         full or partial Return form
/returns                        cross-shift lookup and Return activity
```

The app shell exposes Issues, Issue material and Return actions in its navigation.
Lists become compact cards on small screens and tables on wider screens. Forms
use searchable selectors, bounded quantity controls, clear outstanding counts,
review states, loading and retry feedback, and touch-sized controls. Filters are
kept in the URL where appropriate. All displayed records come from the REST API;
the interface does not simulate notifications, dashboard metrics or Return
success.

## Audit behavior

`ISSUE_CREATED` and `RETURN_RECORDED` events are appended within the same
transaction as their operational data. Audit metadata contains stable IDs,
counts and resulting status, not Receiver contact details, free-text notes,
idempotency keys or request fingerprints. Directory and inventory snapshots in
the Issue itself preserve the evidence needed to understand historical custody.

## Verification

Run the complete workspace checks:

```text
npm run build
npm run typecheck
npm run lint
npm run test
npm run format:check
npm audit --omit=dev
```

Run the destructive-safe Atlas transaction verification against a unique
temporary database (it drops only that generated database in a `finally` block):

```text
cd backend
npm run verify:phase5:atlas
```

Runtime acceptance should use an isolated Atlas database and verify mixed Issue
creation, quantity and serialized stock transitions, consumable depletion,
partial and completed Returns, every serialized disposition, status precedence,
role-scoped visibility, cross-shift Return access, audit creation and same-key
replay/conflict behavior. Drop the temporary database and stop local processes
after testing. Browser acceptance should cover the five routes above at mobile
and desktop widths, including empty, loading, validation, success and retry
states.

## Phase 6 boundary

Phase 5 records authoritative Issue and Return evidence only. It does not call
Brevo, claim that an email was sent, or create fake notification success states.
Phase 6 is responsible for the durable notification outbox, Brevo delivery,
retries, provider identifiers and delivery-status tracking for Issue and Return
proof emails. Dashboard totals, overdue detection, reminder actions and reports
remain Phase 7 work.
